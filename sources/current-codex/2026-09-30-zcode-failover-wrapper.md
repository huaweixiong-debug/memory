# ZCode failover wrapper reliability (2026-09-30)

- In the Morocco pilot repository, `zcode-failover.ps1` now keeps the caller's working directory (including UNC) and invokes the installed `zcode.cjs` through `node.exe`; relative attachments and project context are preserved. If the direct Node entrypoint is unavailable, it fails clearly instead of using the unreliable `.cmd` fallback.
- Persistent provider switching is limited to recognizable quota-exhaustion text or a known numeric code in an explicit code field. Generic 429/rate limits, network/model errors, unknown errors, and timeout do not switch plans. Start Plan remains first; only quota exhaustion advances to the personal Coding Plan and persists that selection.
- The wrapper validates `TimeoutSec`, `MaxAttempts`, `-PlanStart`, and the configured provider; it preserves unknown provider config fields and writes JSON as UTF-8 without BOM. Timeout kills the process tree and does not trigger failover.
- OpenCode used `opencode-go/deepseek-v4.1-flash` / `high`; Codex performed final static acceptance. ZCode CLI used Start Plan OAuth with GLM-5.3-Flash at `max`, without API-key tokens. The real provider config stayed on Start Plan throughout.
- Fake-CLI checks used isolated `USERPROFILE` configs on Windows PowerShell 5.1 and PowerShell 7. They covered quota-to-personal success with identical args, ordinary 429 with `retry after 1315 seconds`, explicit vs embedded numeric code fields, invalid max attempts/provider/config, UNC relative attachments, 1,000,007-character JSON, timeout tree termination, config preservation, and cleanup. The real provider config hash remained unchanged.
- ZCode's two read-only reviews found and drove fixes for the UNC working-directory regression, unusable `.cmd` fallback, output-read race, numeric-code false match, and `MaxAttempts <= 0` false quota report. The last small edge patch was validated by the isolated harness and final Codex review; ZCode did not rerun after that final patch.

The large-JSON regression passed; an unusual descendant retaining redirected handles could extend this post-exit wait.
